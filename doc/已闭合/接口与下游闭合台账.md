### 最小修法依据

- 本项目采用的本地数据库锁处理与 polabel2 的 `fba-query-index` 做法一致：完整事务 rollback 后仅对 1205/1213 做 3 次 50/100/150ms 重试，不重新请求领星。
- polabel2 的上游限流方案是单 lane、capacity=1、最小间隔和远端冷却；本项目保留现有单 worker/内存 limiter，不引入 lane 表、队列、租约或分布式锁。
- GitHub SDK 的可借鉴部分仅是业务请求节奏（约 0.6 秒）和 token 请求单独节奏；不能把其 429/3001008 重试策略套到本次 1205/1213 数据库锁故障上。


## 2026-09-12 数据覆盖口径修正（SC/VC × 销量/广告）

初版结论按"抽样验证管道有数据"口径给出"完整"；复查按"逐店逐日枚举+任务终态全绿"口径修正如下。两种口径的差异必须写明：

- **管道已验证（抽样）**：SC 广告 1-7 月回填+回刷成功、店铺级对账零缺失；VC 广告回填后数据集有行（2/3 月各 3,647/4,143 行）；VC 销量 API 对 1 月仍返回（1/15 实测 14 行、投影 6 行）；SC 销量 4 月起抽样 6 店有值。
- **SC 1-4 月销量**：领星 asinDailyLists API 对约 5 个月前日期基本不返回（40 店请求仅 8 店有零星行）；官方报表导出保留期约 2 个月（6 月起 SUCCESS，5 月前 CANCELLED）。两条路都不可得，1-4 月缺口无法补，维持空缺是上游事实。
- **近期错误任务**：重启打断类（context canceled）无害；领星账号级限流 3001008 致 sc_sales_orders 连续数槽失败——每 30 分钟自动重试，冷却后自动补 30 天窗口，无数据丢失。
- **广告"完整"的边界**：指"与领星返回的 total 精确一致且逐店对账无缺"；广告无官方报表对账层，业务数值的绝对真实仍以领星为源。
- 待验证：expand_stores 全店报告 cron 首次执行（次日 15:00 UTC 后核对任务数与终态）。
